# Database

## Purpose and scope

This MySQL database implements the current Increment 1 ERD for authentication and user management. It contains `roles`, `users`, and `user_sessions`. The repository has no approved complete-system ERD, so entities for events, applications, tasks, attendance, hours, and reports are not included until their later-increment designs are approved.

The ERD has a separate `Role` entity and a persisted `UserSession` entity. This conflicts with `docs/architecture.md` and the traceability matrix, which describe a role enum on `users` and stateless JWT authentication. The SQL follows the ERD because the project task identifies it as the primary schema reference. The token format/lifecycle and resolution of the stateless-versus-persisted session conflict need team confirmation. The schema stores only a 64-character token digest, not a bearer token.

The approved repository stack documents React, Python, and MySQL. This SQL can be called from the Python backend using parameterized statements. No application code is included.

## Requirements

- MySQL 8.0.16 or later; InnoDB and `utf8mb4` support are required.
- A database account with permission to create the database/tables, and a MySQL client.

## Setup

From the repository root, run:

```sh
mysql -u YOUR_MYSQL_USER -p < database/schema.sql
mysql -u YOUR_MYSQL_USER -p event_volunteer_management < database/seed.sql
```

`schema.sql` creates/uses `event_volunteer_management`. It is repeatable for initial setup, but it is not a migration framework and does not alter existing tables. Do not run it against a shared or production database without a reviewed migration and backup plan.

## Files

- `schema.sql` creates the complete schema represented by the current Increment 1 ERD, with keys, constraints, and indexes.
- `operations.sql` documents parameterized SQL statements for Increment 1 registration, account retrieval/management, role assignment, and session lifecycle.
- `seed.sql` inserts the three fictional system role values. User records are intentionally created through the application so a real salted password hash is generated by the application’s password-hashing library.
- `increment_1_smoke.sql` runs transactional smoke checks for account creation/read/update, duplicate-email rejection, and session creation/revocation, then rolls back the probe rows.
- `README.md` documents setup, scope, constraints, and known design decisions.

## Running the smoke checks

After setup and seeding, run:

```sh
mysql -u YOUR_MYSQL_USER -p event_volunteer_management < database/increment_1_smoke.sql
```

Success prints a row beginning `PASS:`. The script creates and drops a stored procedure and rolls back all probe data. It has not been executed in this environment because a local MySQL client/server was not found.

## Relationships and decisions

- One `roles` row can be assigned to zero or more `users`; each user must reference exactly one role. Role deletion is restricted while accounts use it.
- One user can own zero or more sessions; each session belongs to one user. User deletion cascades to its sessions.
- Role values are constrained to Administrator, Event Organizer, and Volunteer. Public registration must assign Volunteer server-side; role authorization and privileged role provisioning remain backend responsibilities.
- `users.email` and `user_sessions.token_hash` are unique. Session rows are indexed by user/expiry and expiry/revocation for lookup and cleanup.
- `password_hash` stores an application-generated salted one-way hash. SQL does not hash passwords.
- `CHECK` constraints are enforced by MySQL starting with 8.0.16, hence the minimum version.

Increment 1 covers authentication and user management. Event management/discovery belongs to Increment 2; applications, assignments, attendance, and hours belong to Increment 3; reporting belongs to Increment 4. Their future operations are not implemented here.
