# Task: Implement the Login Service – Increment 1

## Objective

Implement the Login Service for the Event & Volunteer Management System as part of Increment 1 (Authentication and User Management).

The service must work with the existing User and Role models, the implemented Registration Service, the current MySQL database implementation, and the approved project architecture.

**Approved Technology Stack:**

- Frontend: React
- Backend: Python
- Database: MySQL

Do not introduce a different technology or framework.

## 1. Inspect the Existing Project First

Before implementing anything, inspect the repository and identify:

- The existing User and Role models and their implementation.
- The implemented Registration Service and its password-hashing mechanism.
- The current backend folder structure and coding conventions.
- The existing MySQL database schema.
- The existing SQL operations and database connection/configuration.
- How passwords are stored and retrieved.
- Whether the project already has a session or token-based authentication mechanism.
- The Increment 1 requirements and architecture documentation.
- Existing authentication-related service implementations, if any.
- Existing tests and testing conventions.
- Existing prompt files inside the `prompts` directory.

Use the existing implementation as the source of truth. Do not recreate or duplicate functionality that already exists.

## 2. Implement the Login Service

Create the Login Service in the appropriate location within the existing backend structure.

The service must handle the complete user login process.

### Required functionality

1. **Input validation**

   - Accept the required login information according to the existing project requirements.
   - Validate that the email and password are provided.
   - Reject missing or invalid input with appropriate errors.
   - Apply reasonable input length limits according to the existing model and requirements.

2. **User identification**

   - Retrieve the user associated with the submitted email address from the existing MySQL database.
   - Reuse existing database operations wherever possible.
   - Handle cases where the email address does not belong to a registered user.
   - Do not expose whether a specific email address exists through unnecessarily detailed authentication errors.

3. **Password verification**

   - Verify the submitted password against the stored password hash.
   - Use the same established password-hashing library and verification mechanism used by the Registration Service.
   - Never compare plain-text passwords with stored hashes directly.
   - Never store or log submitted passwords.
   - Reject incorrect passwords with an appropriate authentication error.

4. **Authentication and login success**

   - Authenticate the user only when the submitted credentials are valid.
   - Return the appropriate authenticated user information.
   - Retrieve the user's assigned role using the existing User and Role relationship.
   - Include the user's role information when appropriate for the existing architecture.
   - Do not allow the user to select or change their role during login.

5. **Authentication token or session handling**

   - Inspect the existing architecture to determine whether authentication uses sessions, JWTs, or another approved mechanism.
   - If an authentication mechanism already exists, reuse it.
   - If the architecture requires a token or session but none has been implemented, identify the missing component and explain the proposed solution before introducing a new dependency or changing the architecture.
   - If JWT authentication is already part of the approved design, generate a token using the existing configuration and secure signing mechanism.
   - Never hardcode signing secrets or expose them in source code.
   - Do not introduce an unrelated authentication framework.

6. **Response handling**

   - Return an appropriate success response after successful authentication.
   - Include only appropriate user information, such as user ID, name, email, and assigned role, according to the existing User model.
   - Include the authentication token or session information only if required by the existing architecture.
   - Never return password hashes or other sensitive authentication information.
   - Return meaningful and consistent errors for:
     - Missing login information.
     - Invalid email format.
     - Incorrect credentials.
     - Database failures.
     - Authentication or token-generation failures, where applicable.

## 3. Follow the Existing Architecture

- Use the existing User and Role models.
- Reuse the implemented Registration Service's password-hashing mechanism.
- Follow the project's established naming conventions and folder structure.
- Keep login business logic inside the Login Service.
- Reuse existing database operations rather than duplicating SQL logic.
- Keep responsibilities separated and the implementation maintainable.
- Do not implement registration, logout, password reset, or other authentication services as part of this task.
- Do not implement API routes/controllers or frontend login forms unless the existing architecture explicitly requires them for the service to function.
- Do not modify the existing Registration Service unless a necessary compatibility issue is discovered.

## 4. Security Requirements

- Never store or log plain-text passwords.
- Never expose password hashes in responses.
- Use secure password verification.
- Prevent SQL injection by using parameterized SQL queries or the existing database access mechanism.
- Do not reveal whether an email address is registered through different error messages for unknown emails and incorrect passwords.
- Do not expose internal database errors or sensitive implementation details to clients.
- Do not hardcode secrets, tokens, or signing keys.
- Follow the existing authentication and authorization architecture.
- Do not treat successful authentication as authorization to access privileged functionality.

## 5. Testing and Validation

- Successful retrieval of the authenticated user's information.
- Correct retrieval of the user's assigned role.
- Rejection of missing email.
- Rejection of missing password.
- Rejection of invalid email format.
- Rejection of an incorrect password.
- Rejection of an email that does not belong to a registered user.
- Verification that password hashes are checked using the existing password-hashing mechanism.
- Verification that password hashes are not exposed in responses.

- Safe handling of database failures.

Run the relevant tests and report their actual results. Do not claim tests passed if they were not executed.
