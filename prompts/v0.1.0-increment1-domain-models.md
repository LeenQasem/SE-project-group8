# Increment 1 Backend Models: Consolidated Prompt and Work Record

This document consolidates the three task prompts for the Increment 1 `User`, `Role`, and `UserSession` domain models, including the initial implementation scope, the validation review, the final targeted fixes, and the work completed. It replaces the separate model implementation, improvement, and final-improvement prompt files.

## Consolidated task scope

Implement and refine only the Python domain models for `User`, `Role`, and `UserSession` in Increment 1 (Authentication and User Management). Preserve the existing dataclass architecture, public classes, fields, constructors, and helpers. Do not implement authentication endpoints, repositories, database persistence, an ORM, external dependencies, or functionality from later increments.

### Design and schema requirements

Use `src/database/schema.sql` as the source of truth for persisted attributes, types, constraints, keys, and relationships:

- `Role`: positive `role_id`; `role_name` is one of Administrator, Event Organizer, or Volunteer.
- `User`: nullable-before-insert positive integer `user_id`; `full_name` (150 characters); `email` (254 characters, unique in the database and validated for format in the application); `password_hash` (255 characters); one required `Role`; nullable model timestamps corresponding to database-managed `created_at` and `updated_at`.
- `UserSession`: nullable-before-insert positive integer `session_id`; positive `user_id`; a 64-character hexadecimal SHA-256 `token_hash`; `created_at`, `expires_at`, and nullable `revoked_at` fields. Respect `expires_at > created_at` and `revoked_at IS NULL OR revoked_at >= created_at`.
- A role can be associated with multiple users; each user has one role. A user can have multiple sessions; each session belongs to one user. In-memory checks do not imply database persistence.

Preserve salted scrypt password hashing and safe password verification. Preserve SHA-256 token digesting. Never include password hashes, raw passwords, token hashes, or bearer tokens in public model serialization or representations.

Validate positive integer identifiers while rejecting booleans. Validate user field requirements and schema length limits. Validate timestamps as `datetime` values when supplied. For comparisons, do not mix timezone-aware and timezone-naive datetimes. A user may have both timestamps absent; when both are supplied their timezone awareness must match.

For `User.add_session()`, allow multiple distinct unsaved sessions whose `session_id` is `None`; check duplicate IDs for persisted sessions; retain session ownership checks; and reject adding sessions to an unpersisted user.

Keep the implementation limited to the three models and their necessary in-memory relationships. Do not modify database SQL, frontend files, UML, requirements, other documentation, or unrelated project files. The sole documentation exception is this consolidated prompt/work record under `prompts/`.

## Design notes and limitations

The SQL schema has separate `roles` and `user_sessions` tables. The current Increment 1 class diagram and development plan instead describe a `UserRole` enum and do not show persisted sessions. The implementation follows the SQL schema for persisted model attributes and relationships. The discrepancy remains a project design issue; this work does not edit UML or planning documents.

The repository has no existing Python persistence layer or ORM. The models provide record conversion helpers and in-memory relationships, but do not persist or retrieve records from MySQL. Database uniqueness and foreign-key constraints remain enforced by MySQL. No database schema or operation was changed.

## Work completed

- Implemented dataclass models for `Role`, `User`, and `UserSession` with schema-based validation and `from_record()` / `to_dict()` helpers.
- Added salted scrypt password hashing and verification, and SHA-256 session-token digesting. Sensitive hashes are omitted from representations and public serialization.
- Added ID validation, role-name validation, user field validation, session digest validation, and session expiration/revocation checks.
- Ensured timezone-aware and timezone-naive values are not silently mixed in session comparisons; user timestamps also require matching awareness when both are present.
- Fixed `User.add_session()` so distinct unsaved sessions can coexist, duplicate persisted session IDs are rejected, ownership is checked, and unpersisted users cannot own attached sessions.
- Validated `User.created_at` and `User.updated_at` as optional datetimes and rejected mixed timezone awareness.
- Kept the implementation dependency-free and did not add persistence mechanisms or later-increment functionality.
